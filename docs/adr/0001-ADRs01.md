# ADR 0001 — Decisiones iniciales: modelo de datos, autenticación y frontera cliente/servidor

Fecha: 2026-05-23
Estado: Accepted

## Contexto
El proyecto Habit Tracker es una PWA construida con Next.js 15, TypeScript y Supabase (Postgres) cuya funcionalidad mínima incluye autenticación por email, CRUD de hábitos, registro diario (check-ins), estadísticas (premium), recordatorios por email y pago con Stripe. Se debe priorizar una entrega rápida con buena experiencia UI y aislamiento correcto entre usuarios mediante Row Level Security (RLS).

Esta ADR documenta las decisiones iniciales sobre tres fronteras críticas: modelo de datos, estrategia de autenticación y frontera cliente/servidor.

## Decisión
Se adopta la siguiente configuración inicial:

- Modelo de datos: Esquema normalizado clásico (`users`, `habits`, `checkins`, `subscriptions`, `reminders`) con la columna `best_streak` persistida en `habits` (Alternativa A).
- Autenticación: `Supabase Auth` (email/password) con políticas de RLS en la base de datos (`auth.uid() = user_id`) para controlar acceso a datos sensibles (Alternativa A).
- Frontera cliente/servidor: Interfaz mayoritariamente en Client Components usando el cliente de Supabase y `SWR` para data fetching; el servidor se reserva para webhooks (Stripe), jobs/recordatorios y APIs críticas (Alternativa A).

Razonamiento resumido: estas elecciones priorizan velocidad de desarrollo y coherencia con el stack ya acordado (Next.js App Router + Supabase), reducen código backend custom inicial y optimizan latencia en la UI al costo de añadir responsabilidad en la sincronización de agregados y en el diseño y testing de policies RLS.

## Alternativas consideradas

### Modelo de datos
- Alternativa A — Normalizado + `best_streak` persistido (elegida):
  - Trade-offs: lecturas rápidas para UI y menor carga en endpoints de `/estadisticas`; requiere manejar updates en toggles con transacciones o lógica idempotente para evitar desincronía entre `checkins` y `best_streak`.
- Alternativa B — Normalizado + columnas derivadas actualizadas por triggers/jobs:
  - Trade-offs: muy buenas latencias de lectura (ideal para PWA/offline), pero consistencia eventual y mayor complejidad operativa (migraciones, debugging, monitoring de jobs).
- Alternativa C — `checkins` como única fuente y calcular agregados on-demand:
  - Trade-offs: diseño simple y menor riesgo de datos inconsistentes por escrituras duplicadas; consultas para estadísticas pueden ser costosas y afectar UX sin caching o índices adecuados.

### Autenticación
- Alternativa A — `Supabase Auth` + RLS (elegida):
  - Trade-offs: seguridad fuerte en BD y menos código custom; exige políticas RLS bien documentadas, revisadas y probadas para evitar fugas de datos.
- Alternativa B — `Supabase Auth` + middleware de Next.js:
  - Trade-offs: mejora UX y evita flashes de UI no autorizada; añade complejidad de despliegue y posible duplicación de checks.
- Alternativa C — `Supabase Auth` + validación en APIs server-side:
  - Trade-offs: centraliza validaciones sensibles en backend; necesita más endpoints y coordinación con cliente.

### Frontera cliente/servidor
- Alternativa A — Client Components + Supabase client + SWR (elegida):
  - Trade-offs: desarrollo rápido y coherente con el stack; más JS en el cliente y menos beneficios de SSR para primer pintado.
- Alternativa B — Server Components shell + Client Components puntuales:
  - Trade-offs: reduce JS enviado y mejora TTFB; complica integración con Supabase Auth y el patrón de SWR.
- Alternativa C — UI client-side + APIs server-side para lógica sensible:
  - Trade-offs: combina interactividad y seguridad; requiere diseñar y mantener APIs adicionales.

## Consecuencias esperadas

Beneficios:
- Rápida puesta en marcha y coherencia con la base tecnológica acordada (Next.js + Supabase).
- Experiencia de usuario reactiva, baja latencia en toggles y vistas principales gracias a lecturas optimizadas.
- Seguridad por defecto en la capa de datos mediante RLS, reduciendo superficie de errores en acceso a filas entre usuarios.

Negativas / trade-offs aceptados:
- Necesidad de lógica robusta en la escritura de toggles para mantener `best_streak` consistente con `checkins` (p. ej. transacciones, UPSERTs y mecanismos de retry). Si no se implementa correctamente puede producirse desincronía y discrepancias en estadísticas.
- Mayor dependencia del cliente (más JS entregado) y posible pérdida de optimizaciones de SSR para el primer render. Esto puede afectar Core Web Vitals en dispositivos lentos.
- Alta criticidad en las políticas RLS: un error en las policies puede exponer datos. Requiere pruebas automatizadas o scripts de verificación como parte del pipeline de QA.

## Plan de mitigación
- Implementar tests automáticos de RLS (pruebas descritas en `spec.md`) y checklist de revisión antes de mergear migrations.
- Diseñar la escritura de `best_streak` como operación idempotente y transaccional; añadir backfill/repair job que recalcula `best_streak` desde `checkins` periódicamente.
- Monitorizar métricas de latencia y Core Web Vitals en staging; evaluar migrar partes críticas a Server Components si el impacto es significativo.

## Notas
- Esta ADR debe acompañarse de ADRs puntuales futuros que definan: esquema exacto de tablas/migrations, contratos de API para validaciones de plan y la configuración del job que envía recordatorios por email.
